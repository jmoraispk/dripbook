Day 4 · Claude Code: From Basics to Mastery

How the creator works, and who does what

Boris Cherny’s Workflow: How the Creator Actually

Uses Claude Code

The best evidence for how Claude Code should be used comes from its creator. Boris Cherny, who previously worked at Meta where he was responsible for code quality across the entire company, leads the Claude Code team at Anthropic. His career trajectory from code quality engineering to building AI coding tools gives him a unique perspective on what developers need [49]. Since late 2025, one hundred percent of his own code has been written by Claude Code. He ships ten to thirty pull requests per day and runs five local terminal sessions alongside five to ten remote instances concurrently [1].

Cherny’s workflow is systematic, not casual. He avoids customization, relying on Claude Code out-of-the-box. Each local session uses a distinct git checkout rather than branches or worktrees, preventing conflicts between parallel sessions. Remote sessions are backgrounded via the & operator and shifted with --teleport, though he notes that ten to twenty percent are abandoned due to unforeseen scenarios [2,29].

For coding, Cherny prefers Opus with thinking enabled, citing superior quality, reliability and tool-use capabilities compared to Sonnet. He notes that while Sonnet may be faster per step, the overall throughput is faster with Opus because the first attempt succeeds more often [2,29,47]. As of September 2026, this translates to using Claude Opus 5, the current recommended model for complex workloads, or Claude Fable 5.1 for demanding reasoning and longhorizon agentic work [2].

Knowledge retention is institutionalized through a team-maintained CLAUDE.md file in git. This document logs mistakes, style conventions, design guidelines and PR templates to iteratively improve the AI. Cherny tags colleagues’ pull requests with @.claude to inject new learnings, keeping the file at approximately 2.5k tokens [2]. This is a key insight: CLAUDE.md is not a static configuration file but a living document that improves over time through collective team experience.

His process begins with an iterative planning phase using Plan mode before switching to auto-accept edits, which typically succeeds on the first attempt. Daily operations like commits and PRs are automated via slash commands stored in .claude/commands/, minimizing explicit prompting. A /commit-push-pr command executes dozens of times daily by pre-computing git status inline to reduce model latency. To avert CI failures from formatting inconsistencies, he configures a PostToolUse hook that automatically runs bun run format || true on WriteEdit matches [2,46].

Security is handled by granting specific safe bash commands (e.g., bun run build:*, cc:*) through /permissions, largely eliminating the need for --dangerously-skip-permissions. The dangerous flag is reserved exclusively for sandboxed long-running tasks to prevent repeated interruptions. Cherny emphasizes that providing a verification feedback loop (such as running test suites or browser automation) is critical, boosting final output quality by two to three times. He notes that Claude tests every single change landed to claude.ai/code using the Claude Chrome extension [2,48].

This structured approach ensures code arrives in review already polished, allowing engineers to focus on steering and architectural oversight. The pattern is clear: plan first, then automate the routine steps, verify rigorously and let Claude handle the execution.

The Division of Labor: Human as Orchestrator, Agent as

Builder

One of the most important findings from Anthropic’s research on 400,000 Claude Code sessions is the clear division of labor that emerges between human and agent [6]. In a typical session, people make about seventy percent of the planning decisions (what to do, which approach to take, what counts as done) while Claude makes about eighty percent of the execution decisions (which files to change, what code to write, which commands to run).

This division is not accidental. It reflects both human preference and agent capability. Humans are naturally drawn to planning and decision-making because that is where domain expertise matters most. An accountant directing Claude to build a reconciliation script brings knowledge of the business rules, edge cases at month-end close and the verification criteria that define success. Claude brings knowledge of code structure, library APIs, test frameworks and debugging techniques.

The data shows this division consistently across occupations. Computer and Mathematical Occupations (the largest user group) reach verified success in about thirty percent of their sessions overall [6]. Users from other professions reach verified success about twenty-six percent of the time. Among sessions that produce code, those numbers are thirty-four percent and twentynine percent respectively. Every one of the ten largest non-software occupation groups lands within seven percentage points of software engineers in terms of success rate. Management occupations actually rank highest on verified success, slightly above software engineering occupations.

The greater domain expertise a person brings to a session, the more work Claude does per instruction. In typical novice sessions, each prompt sets off about five Claude actions and roughly 600 words of output. Expert sessions set off action chains more than twice as long (12 actions) carrying five times the output (3,200 words) [6]. This gap appears within every kind of work and every band of task value.

The shape of the collaboration matters for how you think about Claude Code. It is not a replacement for a developer. It is a force multiplier for domain expertise. A senior engineer asking their first Rust question is a beginner at Rust. An accountant who has never used Python but tells Claude exactly which reconciliation rules a Python script must enforce and catches the edge case it mishandles at month-end close is an expert at that task [6]. The tool rewards understanding of the problem domain, not proficiency in a programming language.

Training should focus on developing clarity of problem definition, verification criteria and domain knowledge rather than on learning new syntax or API references. The most effective Claude Code users are not necessarily the best coders; they are the ones who can articulate what needs to be built, why it matters and how to verify that it works.
